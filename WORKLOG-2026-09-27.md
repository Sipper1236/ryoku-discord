- `e3a70bc Add optional live palette integration and rendering improvements`
- `a4ffc4c Follow the Vesktop palette bridge menu setting`

The theme retains its original red and gold colors as the fallback palette. Its optional live palette uses Ryoku Matugen colors exposed to Vesktop/Vencord through QuickCSS. The root custom property `--ryo-palette-mode` defaults to `var(--ryo-bridge-enabled, 0)`, so the Ryoku Palette Bridge integration setting controls whether the theme follows wallpaper colors. Advanced users can set that property to `0` or `1` explicitly. Bridge status roles drive Discord presence colors; unavailable bridge values fall back to the theme's original colors. The artwork is styled through CSS masks so the palette mode can recolor illustrations without shipping a second full theme file.

Rendering work removed permanent row-level `will-change` hints, changes unread animation to a translation, releases animation transforms/filters after completion, and honors reduced-motion settings for supported animations. `README.md` explains setup, palette modes, original artwork credit, and the limits of the performance evidence. `CONTEXT.md` defines the theme's palette terminology. `PERFORMANCE.md` records a live Vesktop check.

The performance check loaded the working-tree theme as the only full theme while keeping bridge QuickCSS and other plugins enabled. It captured short scroll samples through Electron's local Chrome DevTools Protocol. Both the no-theme control and the updated theme had a 16.7 ms median frame interval; the 95th percentile was 49.9–66.7 ms without a full theme and 50 ms with the updated theme. Stalls happened in both conditions. These samples do not establish a measurable speedup or isolate the source of stalls. ## Ryoku Palette Bridge

Repository: `/home/rayyan/Projects/ryoku-palette-bridge`  
Fork remote: `https://github.com/Sipper1236/ryoku-palette-bridge`  
Working branch: `feature/ryoku-settings-lifecycle`

The bridge integration was changed to render the current palette during Vesktop setup. Previously, removing the integration stripped its generated CSS; setting it up again only restored the enabled signal, so Vesktop could remain on fallback colors until another palette-generation event. Setup now reads the authoritative Matugen carrier at `${XDG_CACHE_HOME:-$HOME/.cache}/ryoku/matugen-carrier.json`, invokes Matugen to render the Vesktop template before changing integration state, then writes the generated CSS and enabled marker to QuickCSS. If the carrier is missing or invalid, rendering fails before setup mutates integration state.

A shared `vesktop/quickcss.sh` helper owns the CSS marker and removal rules used by setup and removal. It preserves user CSS, validates marker blocks during setup, removes the bridge-owned blocks, recognizes the old unmarked generated template by normalized digest, and writes the result atomically. User CSS, including `@import` rules, remains before generated palette declarations. `install.sh` installs this helper alongside the standalone remover, and the remover locates it from either a source checkout or the installed share directory.

Regression coverage was added to `tests/install-integrations.test.sh` and `tests/install.test.sh`. It exercises actual Matugen rendering with a nested palette-carrier fixture, first install, idempotent setup, remove/re-enable with changed palette values, retention/order of custom `@import` CSS, missing/invalid carrier failures, and lookup of the installed helper. The core installer test uses stub commands for Ryoku operations. `.github/workflows/ci.yml` runs the Matugen-dependent integration test in an Arch Linux container with `jq` and `matugen` installed. Both shell regression suites passed locally with Matugen 4.2.0; package staging also verified that the packaged remover can locate its shared helper.

These bridge source changes are still uncommitted and unpushed. `.token-savior-cache.json` was already untracked and deliberately left untouched. No official signed package was built or released.

## Ryostore status and remaining work

The Discord theme has **not** been submitted to Ryostore. Ryostore's current catalogues contain Ryoku shell plugins, desktop color schemes, rices, lockscreens, and other Ryoku products; there is no Vesktop/Discord theme catalogue. Its color schemes change Ryoku desktop palettes and cannot install a Vesktop CSS theme. Treating this theme as a shell plugin or desktop color scheme would give it the wrong install behavior and listing.

The upstream Discord theme repository has no declared license (`licenseInfo` was null), and the Ryostore submission form requires confirmation that the submitter has redistribution rights for the item and preview. The repository's README also credits the upstream author and uses upstream screenshots. Rights for the upstream CSS and artwork must be resolved before redistributing those files through Ryostore. A decision is also needed on whether to propose a dedicated Vesktop theme category / installation path or leave this theme available through its GitHub repository.
